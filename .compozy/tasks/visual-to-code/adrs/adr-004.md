# ADR-004: Canvas undo of model edits in VSCode through the server history

## Status

Accepted (owner, 2026-10-18; resolves Q8, amends ADR-003)

## Date

2026-10-18

## Context

ADR-003 kept the model-edit history on the server for the dev server only. In the VSCode preview,
canvas Ctrl+Z only undid layout changes. Model edits had to be undone in the `.c4` editor, and that
path never touches the manual-layout snapshot, which is written through the filesystem. After a
text undo, the snapshot still holds the removed node and the view reports drift.

The owner asked that Ctrl+Z on the canvas work in VSCode too, without going to the text, so that
the snapshot stays in sync.

Facts from the code:

- `LikeC4ModelChanges` already records the texts before and after each change and checks them
  before restoring. It only skips this when an LSP connection exists (`recordHistory`, `restore`).
- The editor actor already handles model entries in its history: an undo of a model entry goes
  through `port.undoModelChange`, then sets `refreshManualLayout`, which re-applies the latest
  layout to the snapshot. The snapshot sync therefore comes for free once the port supports undo.
- With an LSP connection, writes go through one `workspace/applyEdit` and the extension saves the
  modified documents (`modifiedUris`).

## Decision

- `LikeC4ModelChanges` records the history with and without an LSP connection. Undo and redo
  restore the recorded texts through `applyWorkspaceEdits`: one `WorkspaceEdit` with an LSP
  connection, filesystem writes without one. The `stale-undo` check is unchanged.
- The VSCode extension forwards two new messenger requests from the preview to the LSP requests
  `likec4/undo-change` / `likec4/redo-change`, and saves the documents listed in `modifiedUris`, as
  for `change-view`.
- The VSCode preview port implements `undoModelChange` / `redoModelChange` and throws on failure.
- The `.c4` editor's own undo keeps working. Its effect on the snapshot is not covered (non-goal).

## Alternatives Considered

### Alternative 1: Run VSCode's `undo` command on the modified document

- **Description**: the extension focuses the modified document and runs `undo`.
- **Pros**: reuses the editor's undo stack.
- **Cons**: needs the document focused, undoes whatever the user typed last (not necessarily the
  canvas edit), and cannot undo a multi-file edit as one step. No stale check.
- **Why rejected**: it can revert the wrong change silently.

### Alternative 2: Write snapshots through the same `WorkspaceEdit`

- **Description**: route the manual-layout snapshot write through `WorkspaceEdit`, so a text undo
  reverts both.
- **Pros**: the `.c4` editor's undo stays in sync with the snapshot.
- **Cons**: the snapshot is saved after the model sync, in a separate step, so it would still be a
  second undo stop. The snapshot file would open as a dirty editor in VSCode.
- **Why rejected**: it does not give a canvas Ctrl+Z, which is what the owner asked for.

## Consequences

### Positive

- One Ctrl+Z history on the canvas in both hosts, and the snapshot stays in sync.
- Undo in VSCode is itself a text edit, so the `.c4` editor's redo/undo still apply to it.

### Negative

- The history is lost when the language server restarts (VSCode window reload).
- Two undo paths exist in VSCode, and only the canvas one keeps the snapshot in sync.

### Risks

- A user edits the `.c4` file by hand, then presses Ctrl+Z on the canvas: the undo is refused with
  `stale-undo`, as in the dev server.

## Implementation Notes

- Remove the `Connection` guards in `recordHistory` and `restore`. Return `modifiedUris` from undo
  and redo so the extension can save.
- Extend `undo.spec.ts` with the faked connection from `__test__/memfsWorkspace.ts`.
